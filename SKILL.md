# SnapGene Plasmid Builder Skill

## Purpose

Use this workflow when the user provides one or more SnapGene `.dna` template files and wants a new plasmid simulated by Gibson Assembly, Golden Gate, PCR-based replacement, or related subcloning.

The workflow is optimized for laboratory plasmid construction where the final deliverables must include:

- final SnapGene `.dna` file(s)
- correct plasmid sequence and topology
- preserved/normalized feature annotations and colors
- correctly displayed primers
- primer reuse based on the user's latest primer table
- updated primer table when new primers are required
- recommended colony-PCR validation primers
- a manual construction history in SnapGene Description when native SnapGene History cannot be generated
- an ultra-compact construction checklist in the user's laboratory format

The latest user-supplied primer table is the authoritative source for primer names.

---

# 1. Expected Inputs

Prefer receiving all of the following in the same task:

1. **Backbone/parent `.dna` file(s)**
2. **Insert/template `.dna` file(s)**
3. **Latest primer table** (`.csv` or spreadsheet)
4. **Target plasmid name(s)**, e.g. `pJC2642`
5. **Construction goal**, e.g. replace T7-idgS-sfp with Para-idgS-sfp while preserving EGFP homology arms
6. Optional constraints:
   - Gibson vs Golden Gate
   - sequences/features that must be retained
   - host strain / medium / antibiotic / temperature
   - desired colony-PCR strategy

If the user uploads SnapGene text history, automatically parse it into the compact construction-list format described in Section 10.

---

# 2. Core Principle: Modify From a Native SnapGene Template

Whenever possible, **do not create the final `.dna` file from scratch**.

Use the backbone `.dna` file as the structural template and preserve its native SnapGene metadata. Replace only the sequence/annotation regions that are genuinely changed.

Preserve from the native backbone whenever appropriate:

- DNA topology
- double-stranded state
- circular/linear state
- methylation/topology flags
- feature display settings
- feature colors
- feature direction
- primer XML/display conventions
- notes/description fields that remain relevant
- other intact SnapGene packets/metadata

For circular dsDNA plasmids, clone the topology/flags from the real backbone instead of hard-coding a generic value.

After generation, verify that SnapGene opens the product as the intended molecule type, typically **circular double-stranded DNA**.

# 3. SnapGene Native History Policy

Do **not** fabricate a fake native SnapGene History tree.

Native SnapGene History contains proprietary construction/ancestor data and should only be generated by SnapGene itself or by a verified compatible implementation.

If native History cannot be safely generated:

1. keep the native History absent rather than forging it;
2. write a structured **Manual Construction History** into the SnapGene **Description** field;
3. include legacy primer-name mappings and construction ancestry there.

Use wording such as:

```text
Note:
This record is a manually generated construction history and is not the native SnapGene History tree.
```

# 4. Feature Handling and Colors

## 4.1 Preserve source feature styling

For unchanged features, inherit the feature from the source `.dna` file rather than recreating it.

For inserted features, copy the original feature annotation and styling from the insert template whenever possible, including:

- name
- type
- direction
- color
- qualifiers
- translated reading frame where applicable

## 4.2 Do not invent broad overlay features

Do not add a large `cargo`, `insert`, or other feature spanning many existing features unless explicitly requested. Such overlays can obscure the intended SnapGene color hierarchy.

## 4.3 Feature integrity check

Before finalizing, verify that:

- genes remain in-frame where expected
- promoter/RBS/gene/terminator boundaries are correct
- homology arms that the user requested to retain remain present
- L/R, att sites, CAST elements, resistance genes, origins, gRNA features, etc. remain intact unless intentionally modified
- feature colors match their source templates

# 5. Primer Table Is Authoritative

The **latest user-uploaded primer table** is the official naming source.

Typical columns may include:

```text
Primer_Name
seq
lenth
Description
```

Column names may vary; infer equivalent columns where obvious.

## 5.1 Primer sequence normalization

For matching:

- uppercase sequence
- remove spaces
- remove hyphens
- normalize DNA alphabet where appropriate
- compare full primer sequence exactly first

## 5.2 Primer reuse priority

When a primer is needed, use this order:

1. exact sequence match in the current primer table
2. existing primer in the table that already binds the correct Gibson/Golden Gate interface and has suitable orientation
3. existing primer in the table that produces an appropriate validation amplicon
4. only then design a new primer

Never create a duplicate new primer if an identical sequence is already present in the current primer table.

## 5.3 Legacy SnapGene primer names

A template `.dna` may contain old names that differ from the primer table.

If the sequence matches a primer in the current table:

- display/use the primer-table name as the current official name
- record the old name as a legacy alias in Description

Example:

```text
Primer normalization:
Legacy primer: Para-RBS1-idgS-vector-R
Current primer: JC2525R
Sequence matched to laboratory primer table.
```

Old/obsolete primer names do not need to remain as active displayed primers unless they are experimentally useful.

## 5.4 New primer naming

If new primers are unavoidable:

1. inspect the current primer table for the highest/next available `JC` number;
2. follow the table's existing naming convention;
3. avoid duplicate IDs;
4. use `F`/`R` orientation suffixes consistently;
5. append all newly designed primers to a returned **updated primer table**.

Do not silently overwrite the user's original primer table. Return a new updated copy.

## 5.5 Primer Tm design preferences

For **newly designed primers**, use the following soft targets unless the user specifies otherwise:

- **PCR template-annealing region Tm:** preferentially **58–60 °C**, ideally near the middle of that range.
- **Gibson homology/overlap Tm:** preferentially **50–55 °C**. Choose the overlap **length** needed to reach this Tm rather than using a fixed number of base pairs.

These are design preferences, not absolute rejection criteria. An existing primer from the authoritative primer table should generally be reused when it is otherwise suitable, even if its Tm is modestly outside the preferred range.

Use a consistent Tm calculation method within the same construction task. Distinguish clearly between the Tm of the **3′ template-annealing region** and the Tm of the **5′ Gibson overlap**.

# 6. Gibson / Golden Gate Primer Display in SnapGene

Primer display must reflect **which molecule is being viewed**.

## 6.1 PCR template or PCR-intermediate display

When a primer is displayed on the **original PCR template** or an unassembled PCR intermediate:

- the **5′ Gibson homology/overlap tail** is a non-hybridizing primer component
- the **3′ template-specific region** is the annealing/binding region
- do not mark a non-template 5′ tail as annealing to the original PCR template
- preserve primer direction
- store or calculate the annealing Tm from the 3′ template-specific region

For Golden Gate primers on the original PCR template, likewise distinguish non-template 5′ additions (protective bases, Type IIS site, designed overhang) from the 3′ annealing region.

## 6.2 Final assembled-plasmid display

For a **final assembled plasmid `.dna` file**, use a different display rule:

- if the **entire primer sequence is present continuously in the final assembled plasmid**, map/display the **full primer sequence as one continuous match**
- do **not** force the former Gibson/Golden Gate 5′ tail to remain visually folded out merely because it was non-hybridizing on the original PCR template
- this avoids making a correctly assembled junction look as though part of the primer is mismatched
- retain the original molecular meaning in **Description**, including the original 3′ annealing region and the 5′ Gibson overlap/Golden Gate addition
- if the full primer sequence is **not** present continuously in the final plasmid, keep the truly non-hybridizing 5′ component displayed separately

Thus, primer display on the final product is a **final-sequence mapping view**, while Description preserves the **construction-history view**.

The final `.dna` should remain visually consistent with native SnapGene primer behavior and should not use generic feature annotations as a substitute for primer objects.

# 7. Colony-PCR Primer Selection

For every newly constructed plasmid, recommend **one primary colony-PCR primer pair** unless the user asks for more.

## Priority order

1. existing primers from the current primer table near the Gibson/Golden Gate interface
2. existing template primers near the interface that can be normalized to primer-table names
3. existing internal validation primers
4. newly designed primers only if no suitable existing pair exists

## Preferred design

Prefer a **junction PCR**:

- one primer in the retained backbone
- one primer in the newly inserted/replaced region

This should test at least one of:

- correct insertion
- correct orientation
- correct assembly junction
- discrimination from the original parent plasmid

Avoid two primers entirely inside the insert when that would also amplify free template/parental material or fail to test the assembly junction.

Avoid primer pairs that give the same expected band from the parent plasmid.

Prefer practical amplicons, typically a few hundred bp to roughly 2 kb, unless a longer product is specifically advantageous.

If an apparently convenient primer is located in a sequence also present in the parent (for example `lacI`), check for false-positive amplification before recommending it.

Report the expected product size.

# 8. Assembly Simulation

For each target plasmid:

1. parse all source `.dna` files
2. identify the exact retained backbone interval(s)
3. identify the exact insert/template interval(s)
4. confirm orientation
5. confirm expected junction sequences
6. identify or design PCR primers
7. simulate PCR products including non-template primer tails
8. assemble the expected final sequence
9. transfer relevant source features with coordinate remapping
10. normalize primers to the current primer table
11. add recommended colony-PCR primers
12. add Manual Construction History to Description
13. preserve the parent SnapGene display/topology metadata
14. validate the final sequence independently

For Gibson, verify overlap identity at every junction. For newly designed overlaps, preferentially choose an overlap length that gives an overlap Tm of **50–55 °C**.

For Golden Gate, verify Type IIS cleavage logic, overhang sequence, orientation, and absence/presence of unwanted internal sites where relevant.

---

# 9. Mandatory Validation Before Delivery

Do not deliver a final `.dna` until all applicable checks pass.

## Sequence checks

- final length matches the simulated assembly
- junctions are exactly as designed
- inserted CDS sequences match the requested template
- no unintended extra bases at PCR/Gibson/Golden Gate boundaries
- preserved regions remain unchanged

## SnapGene checks

- molecule opens as intended (usually circular dsDNA)
- features are visible
- feature colors are sensible and inherited from sources
- primers are visible
- on final assembled plasmids, any primer whose full sequence exists continuously in the product is displayed as a continuous full-length match; truly absent 5′ additions remain non-hybridizing
- primer directions are correct
- Description contains the manual construction history

## Primer checks

- all official primer names are consistent with the latest primer table
- no duplicate sequence was unnecessarily given a new primer ID
- new primers are included in the updated primer table
- colony-PCR amplicon size is reported and is diagnostic

# 10. Compact Laboratory Construction Checklist

When the user asks for a **构建清单 / 实验清单**, use the following ultra-compact format.

Use current **UTC+8 / Beijing time**, accurate to the minute.

Do not write a report-style explanation inside this checklist.

Example:

```text
时间：2026-09-07 14:40

构建 pJC2642（目标：将原 T7 表达盒替换为 Para-idgS-sfp）

T = pJC2641
P = JC2330F/JC2330R
F1 = 12776

T = Para-RBS1-idgS
P = JC2524F/JC2524R
F2 = 5825

pJC2642/Gibson = f1+f2
DH5a，LB，kan30，30℃


构建 pJC2643（目标：将原 T7 表达盒替换为 Tac-idgS-sfp）

T = pJC2641
P = JC2330F/JC2330R
F3 = 12776

T = pMMB207-idgS-sfp
P = JC2522F/JC2524R
F4 = 6084

pJC2643/Gibson = f3+f4
DH5a，LB，kan30，30℃
```

## Rules

- start with `时间：YYYY-MM-DD HH:MM`
- each plasmid starts with `构建 pXXXX（目标：...）`
- each PCR fragment is exactly:

```text
T = template
P = forward/reverse
F1 = length
```

- **F numbering is continuous across the entire checklist**, including multiple target plasmids
- Gibson line:

```text
pXXXX/Gibson = f1+f2
```

- Golden Gate line:

```text
pXXXX/GoldenGate = f1+f2+...
```

- end with strain, medium, antibiotic, temperature
- if an experimental condition is unknown, use `“___”` rather than inventing it
- provide the checklist as directly copyable plain text/TXT

# 13. Behavior When Information Is Missing

Do not invent biological sequences or experimental conditions.

If the exact sequence can be resolved from the uploaded `.dna` files, resolve it directly rather than asking the user to paste it.

If a noncritical culture condition is unknown, use `“___”` in the compact checklist.

For complex construction tasks, make a best-effort complete design from available files rather than stopping at unnecessary clarification.

---

# 14. Portability

This file is intentionally platform-neutral.

It can be used as:

- a Codex/Agent Skill `SKILL.md`
- a project instruction file
- a custom GPT/project prompt
- an instruction attachment in another AI platform
- a laboratory SOP for an agent that has access to SnapGene `.dna` parsing/writing tools

The agent must have the ability to read/write the binary `.dna` format or use an appropriate SnapGene-compatible library. If it cannot safely write `.dna`, it should still produce the sequence design, primer table updates, Description text, and construction checklist, and should not pretend that a valid SnapGene file was created.
